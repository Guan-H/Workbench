# 项目初始化规范

## 1. 基本原则
- 初始化前读取 `docs/prd/PRD.md`、根目录 `AGENTS.md`、`docs/rule/CODING.md`、`docs/rule/STACK.md`。
- 先分析业务，再确认架构，最后生成工程。
- 相同技术栈和项目类型优先沿用一致的命名、模块组织和分层风格；不同技术栈不机械照搬 Java 结构。
- 只生成最小可运行工程，不提前实现 PRD 的业务功能。
- 未经确认，不变更已确定的架构或技术栈。

## 2. 阶段一：业务与架构方案（禁止写代码）
先输出简洁方案，包含：
1. **业务模块**：名称、职责、主要功能及模块依赖。
2. **技术选型**：语言、框架、数据库、构建工具、必要依赖。
3. **架构类型**：优先简单、成熟方案；说明关键取舍。
4. **拟建目录树**：展示项目根目录及前端、后端、文档、数据库脚本的位置与职责。
5. **初始化范围**：必要的启动、配置、质量工具和公共能力。

要求：
- 模块按业务边界划分，不按数据表机械拆分。
- 模块内部使用该技术栈惯用的分层方式；Java 遵循 `docs/rule/CODING.md` 的业务模块分包规则。
- 禁止不必要的微服务、复杂分层、空抽象和占位文件。
- 有多个可行方案时推荐一个默认方案并简述理由；按 `STACK.md` 的后端与前端偏好评估，关键技术选型必须由用户确认。

**确认门禁：用户明确确认架构、目录与技术选型后，才能开始创建工程。**

## 3. 项目总目录约定
前后端分离项目采用下列**目标布局**。其中 `AGENTS.md`、`README.md` 与 `docs/` 是固定的文档骨架；`frontend/`、`backend/`、`database/` 在用户确认对应工程方案后创建，不为了填满目录而提前创建：

```text
project-name/
├── AGENTS.md                  # 唯一 AI 规则入口与工作行为规范
├── README.md                  # 工程说明、启动与调试
├── docs/
│   ├── rule/
│   │   ├── CODING.md          # 代码风格、注释、分包及质量
│   │   ├── STACK.md           # 技术栈默认偏好
│   │   └── INIT.md            # 项目初始化协议
│   ├── prd/
│   │   └── PRD.md             # 已确认的产品需求
│   └── architecture/
│       └── architecture.md    # 已确认技术方案
├── frontend/                  # 前端工程
├── backend/                   # 后端工程
└── database/
    └── migrations/            # 数据库迁移脚本
```

- 上述是前后端分离项目目标布局，不代表任何项目都必须有前端、后端或数据库；具体工程目录以 PRD 和用户确认的方案为准，不能创建空代码或占位文件。
- `docs/rule/` 集中管理三份开发规范；`docs/prd/PRD.md` 是权威 PRD；`docs/prd/` 存放权威 PRD，`docs/architecture/` 存放确认后的架构方案；避免多份互相矛盾的副本。
- 前后端各自保持对应框架的标准内部结构；Java 后端遵循 `docs/rule/CODING.md` 的按业务模块分包约定。
- 初始化前展示这棵目录树及省略/新增理由，必须经用户确认后才创建。

## 4. 阶段二：最小工程骨架
- 优先官方脚手架或成熟构建工具，生成标准工程。
- 按确认方案建立目录和必要依赖、启动入口、环境配置。
- 配置必要的格式化、代码检查和基础验证；提供启动/调试说明。
- 严格执行 `docs/rule/CODING.md`，保证代码可读、可导航、可调试。
- 业务模块可先在架构方案中列明，无需提前创建全部 Controller、Service、Mapper、页面。仅生成启动、构建与验证必需的公共能力；未被 PRD 或确认方案要求的鉴权、缓存、消息队列等不提前生成。

严禁：
- 未经要求一次生成大量业务代码、API、页面或数据库操作。
- 生成空实现、占位类、无意义目录或未来可能用到的复杂抽象。
- 引入未经确认的新框架，或使用一行式压缩源码、伪代码工程。

## 5. 配置与环境管理
- 明确开发、测试、生产环境的配置边界；按需提供环境变量示例（不含真实密钥）。
- 数据库、Redis、第三方服务的地址及凭据必须可配置，不硬编码到源码。
- README 说明必备依赖、环境变量、初始化和启动命令，保证环境可复现。
- 真实凭据不得提交仓库；添加合适的忽略规则，不预先引入无用基础设施。

## 6. 阶段三：初始化验收
- **架构**：目录及模块与确认方案一致，职责清晰。
- **风格**：命名、分层、格式遵循 `docs/rule/CODING.md`。
- **工程**：完整源码、依赖和配置，具备对应 IDE 的导航与调试条件。
- **验证**：实际执行可用的依赖解析、编译、启动、基础测试或检查。
- **范围**：确认未抢先实现 PRD 的业务功能，也没有超出已确认范围生成基础设施。

未执行的验证明确列出原因，不得虚报成功。

## 7. 交付与停止点
初始化完成仅汇报：
1. 已确认的架构和业务模块。
2. 实际生成的项目目录。
3. 已完成的基础配置。
4. 构建、启动、检查的真实结果。
5. 遗留问题及下一步建议。

**初始化验收后停止；除非用户另行指示，不进入业务功能开发。**
