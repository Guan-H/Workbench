# 通用代码规范

## 1. 代码风格
- 命名明确，遵循语言和框架惯例；同一项目保持统一风格。
- 源码正常缩进、换行，禁止把整个类、函数或文件压缩成一行。
- 文件职责清晰；避免超长方法、重复代码和无意义的抽象。
- 注释重点解释业务原因、边界条件及非直观逻辑，不重复代码字面含义。
- 不生成混淆源码、伪代码代替正式实现；主要类应各自独立成文件。

## 2. 架构与模块
- 优先按业务领域组织模块；模块内组织遵循当前语言和框架惯例。Java/Spring Boot 采用下文规定的模块内分层，不强加给其他技术栈。
- 模块边界清晰；不得跨模块直接操作其他模块的数据访问层。
- 公共模块只承载可复用基础能力，不得反向依赖业务模块。
- 遵循现有项目组织方式；不未经确认改变架构。
- 只建立有实际用途的目录和抽象，不为未来设想堆砌空文件。

## 3. 工程与质量
- 使用语言/框架标准工程结构，具备真实可用的构建及运行配置。
- 保证源码可被相应 IDE 正常识别、索引、跳转和断点调试；不使用压缩源码。
- 异常处理、日志和 API 风格统一；不吞异常，不记录敏感信息。
- 关键业务逻辑具备适当测试；能检查时执行检查，失败如实说明。
- 禁止硬编码密钥、密码或敏感凭据，外部输入须校验。

## 4. Java / Spring Boot 专属规则

### 4.1 目录（按业务模块分包，模块内分层）
```text
src/main/java/com/example/project/
├── ProjectApplication.java
├── modules/
│   ├── user/
│   │   ├── controller/
│   │   ├── service/
│   │   │   └── impl/
│   │   ├── mapper/
│   │   ├── entity/
│   │   └── dto/
│   └── order/
│       ├── controller/
│       ├── service/
│       │   └── impl/
│       ├── mapper/
│       ├── entity/
│       └── dto/
├── common/
│   ├── constant/
│   ├── enums/
│   ├── exception/
│   └── util/
└── config/
```
- 包路径与文件目录一致；按需增加 `vo`、`convert` 等目录，不生成无意义空目录。
- 使用 Maven/Gradle 标准结构：`src/main/java`、`src/main/resources`、`src/test/java`。
- Spring Boot 启动类位于可覆盖业务模块组件扫描的根包。

### 4.2 命名
- 类名大驼峰：`OrderController`；变量/方法小驼峰：`createOrder`。
- 常量全大写下划线：`MAX_RETRY_COUNT`。
- Service：`OrderService`；实现：`OrderServiceImpl`；Mapper：`OrderMapper`。
- 实体：`OrderEntity`；请求：`CreateOrderRequest`；响应：`OrderResponse`。
- 数据库表和字段使用 `snake_case`；API 路径小写并以连字符分隔单词。

### 4.3 分层职责
- Controller：接收请求、参数校验、调用 Service、返回响应。
- Service：实现业务规则、事务边界与业务编排；接口及 `impl` 依既定结构组织。
- Mapper：数据库访问，不承担业务逻辑。
- Entity：持久化实体；DTO/Request/Response：接口数据契约，不直接暴露 Entity。
- Common：跨业务模块复用能力；Config：基础设施配置，不放业务逻辑。

### 4.4 格式与可调试性
- Java 统一 4 空格缩进、UTF-8、合理 import、正常代码块换行。
- 完整依赖、启动入口与配置；支持 IntelliJ IDEA 导入、索引、导航、编译和断点调试。
- 优先构造器注入，事务放在合适的 Service 方法边界。
- MyBatis-Plus 查询需有明确条件或显式确认，避免意外全表操作。
- SQL 参数化，禁止拼接不可信输入；Redis Key 命名清晰，按业务需要设置 TTL。

## 5. 注释规范
- **原则**：注释说明“为什么”和业务约束，不复述“做了什么”；优先通过清晰命名和代码结构表达意图。
- **类/接口**：对外 API、公共组件及承担重要业务职责的类，说明用途和边界；简单且职责显然的内部类可省略。
- **公开方法**：复杂业务方法、公共接口、SDK/API 方法应说明用途、关键参数、返回值及可能的异常；简单的 getter/setter 和显而易见的方法不强制注释。
- **字段/常量**：含业务含义、特殊取值、单位、时区或状态约束时必须说明；含义明确的字段不重复注释。
- **复杂逻辑**：金额计算、状态流转、权限判断、缓存一致性、兼容性处理等，说明规则来源、边界条件或取舍原因。
- **Java**：对需文档化的类型和方法使用标准 Javadoc `/** ... */`；必要时使用 `@param`、`@return`、`@throws`，内容应与实际代码一致。
- **TODO/FIXME**：仅标记真实待办，写明具体问题和处理条件；有任务系统时关联任务编号，禁止长期保留无主占位注释。
- **禁止**：逐行翻译代码、无意义模板注释、过期或错误注释、注释掉的大段废弃代码，以及在注释中写入密钥或敏感数据。
- **同步维护**：修改业务逻辑或接口时检查并更新相关注释；优先保证注释正确而不是数量多。

## 6. 代码变更与数据库安全
- 修改前阅读现有实现、依赖调用与测试；以最小必要改动完成任务。
- 不随意重命名、删除、重构无关代码；不得覆盖用户尚未提交的修改。
- 变更公共接口时检查受影响调用方，必要时补充回归测试。
- 改表前核对现有结构和关联；使用可追踪的迁移脚本管理结构变化。
- 未经确认不得删除表、字段或业务数据；生产数据操作先说明影响和风险。
- 保持实体、映射与表结构一致；按实际查询设计索引，避免无条件全表操作。

## 7. 前后端接口契约
- 前后端统一约定接口路径、HTTP 方法、请求及响应结构、错误码。
- 前后端数据契约的字段名称、类型、可空性必须一致；前端使用 TypeScript 时，其类型定义应与后端 DTO/接口契约对应。
- 项目采用 OpenAPI 时，以确认的接口契约为准；可用时优先自动生成类型。
- 修改接口前评估兼容性，并同步检查调用方、文档与相关测试。
- 不直接向前端暴露持久化 Entity 或敏感字段。

## 8. 其他技术栈
- 继承通用规则，采用对应语言、框架的标准目录与开发惯例。
- 不将 Java 的 `controller/service/mapper` 分层机械套用到非 Java 项目。
